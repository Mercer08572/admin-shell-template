# Agent Tasks

每个可交付功能使用一个独立 Markdown 文件。文件名建议为 `<模块>-<编号>-<简述>.md`，例如 `CUS-001-customer-import.md`。

任务说明的价值在于：**验收标准先写清楚，实现才不会漂**。写完后照做，不要在执行过程中悄悄扩大范围。

## 任务模板

```markdown
# <任务编号> <标题>

## Context

业务背景、关联页面，以及后端契约位置（接口文档 / 代码路径）。

## Scope

- 明确要实现的内容。

## Out Of Scope

- 明确本次不处理的内容。

## API Contract

- METHOD /api/v1/path
- 请求、响应、错误码与权限约束。
- 使用 mock 时，说明要同步补的桩数据与错误分支。

## 验收标准

- 可照做的验证步骤与期望现象（含 320 px 窄屏与错误分支）。

## 影响面

- 会改到哪些目录 / 组件；是否会改到外壳、传输层或 mock 的既有约定。
```

## 本模板自带的示例任务

| 文件                       | 内容                                                      |
| -------------------------- | --------------------------------------------------------- |
| `CUS-001-customer-demo.md` | 客户 + 联系人示例模块（已实现，可作为任务说明的参考写法） |

## 提示

- 涉及外壳布局的改动，先读 `docs/architecture.md` 的「布局契约」，那里记录了两条实测踩过的坑。
- 动了 mock 行为时，同步改 `src/api/mock/mock.test.ts`；动了页面行为时，同步改对应的 Playwright 用例。
